# 阶段 1：现版本与之前版本的区别（公开版）

公开版整理日期：2026-09-23。

本文保留功能变化、使用方式、参考项目和当前限制；省略业务样本标识、内部评测明细、内部实现路径、配置阈值与部署信息。文中的文档 key 均为虚构示例。

## 一、先说结论

这一阶段升级的是文档处理底座：系统不仅保存供检索使用的文字切片，还保存这些内容属于哪份文档、哪个版本、哪一页、哪个原文块。

结构化文档、来源追踪、重复导入和版本身份保护已经实现并有验证记录；但新索引的问答质量验收尚未通过。因此不能把“功能已经实现”理解为“已经可以正式替换旧索引”。

本文中的版本含义：

- **之前版本**：阶段 0 的文档导入与切分方式。
- **现版本**：本地工作区已实现的阶段 1 文档 IR 改造，不是一个已经发布的正式软件版本。
- **本次上传范围**：仅发布这份说明文档，不包含工作区中的阶段 1 功能代码、原始业务文档、评测快照或配置凭据，也不切换运行中的索引。

## 二、用户能感知到的变化

### 1. 从“保存文字切片”变成“同时保存文档结构”

之前主要围绕 MinerU 生成的 Markdown，按标题和长度切分。标题、文字和图片处理已经存在，但缺少统一的文档结构及贯穿全链路的来源契约。

现在增加统一的文档中间表示，简称 IR：`Document → Section / Block → Chunk`。

- Document：整份文档，保存来源、文档身份、版本和解析器信息。
- Section / Block：章节与内容块，例如段落、表格、图片、代码和公式。
- Chunk：供检索使用的切片，指向原来的章节和内容块。

保存的信息包括标题层级、原文范围、页码、坐标、表格单元格与跨页关联、图片来源及哈希、OCR 文本，以及解析状态和错误。

这些信息取决于源格式和解析结果：PDF 有页面定位，普通 Markdown 通常没有物理页码，系统不会凭空编造页码；保存 OCR 结果也不代表 OCR 识别一定正确。

### 2. 从“依赖切片编号”变成“分层识别身份”

之前的样本文档切片缺少稳定来源 ID 和页码，数据库编号不足以表达跨版本关系。

现在分别记录：

- `document_id`：是哪份文档。
- `revision_id`：是这份文档的哪个版本。
- `page_uid`：在可信匹配下，追踪跨版本的页面身份。
- `lineage_id`：在可信匹配下，追踪跨版本的内容块身份。
- `chunk_id`：当前版本、当前切分配置下的具体切片。

相同源文件在相同解析结果和切分配置下重复导入，相关 ID 可稳定重现。调整切分长度或修改内容后，切片数量和切片 ID 可以变化，不强行保持相同。

例如在 PDF 前面新增一页，旧第 2 页可能变成新第 3 页。匹配足够可靠时可以保留它的页面身份，但引用应显示新版本实际的第 3 页。内容重复或匹配不明确时，不会猜测它们是同一页、同一块。

### 3. 从“按标题切分为主”变成“先尊重内容结构”

现在先按章节和内容块组织，再处理长度限制。长表格按行拆分并重复表头，代码尽量按行，普通文本尽量按句子边界；切片保留原文块引用和标题路径。

这不是承诺完全不拆分，也不表示切片越多越好。已有样例中新旧切分方式产生了不同数量的切片，但输入和生成时点并不完全相同，不能直接当作质量提升证据。

### 4. 从“引用某段文字”变成“引用可追溯的原文位置”

现在索引和查询返回会携带文件来源、版本、页码、内容块及可用的坐标信息，能够追溯引用来自哪里。

这里要区分两件事：

- 引用可定位：知道模型引用的是文件中的什么位置。
- 引用正确：该位置的内容确实支持模型给出的结论。

本阶段已经验证前者；后者仍有评测失败，不能混为一谈。也不能把定位元数据等同于已经实现了前端 PDF 自动跳页、高亮的阅读器。

### 5. 处理步骤更清楚，失败更容易排查

导入链路拆成解析、规范化、切分、图片等信息补充、向量化与索引写入。MinerU 的输出先经适配器转换为统一 IR，后续步骤不再直接依赖 MinerU 的私有结构。

新增可回读的 `document.ir.json`、结构化错误、有限重试、异常隔离和任务状态记录。损坏解析制品不会直接当作正常文档继续入库。当前仍未接入完整的运营告警渠道。

## 三、document_key 到底怎么用

`document_key` 是调用方为“这份逻辑文档”指定并保存的固定标识，不是文件名，也不是要从切片中寻找的数据库编号。

### 正常更新的例子

1. 第一次上传说明书时，指定 `document_key = example-manual`（虚构示例）。
2. 保存这个 key；下一次上传修订版时仍传同一个 key。
3. 系统从注册记录中找到上一版 IR，检查是否存在明显的身份冲突，再进行版本对齐。
4. 检查通过且入库成功后，用新版切片替换目标索引中这份文档的旧版切片。

调用方不必每次手动寻找上一版 IR，但需要保存并复用 key。当前没有在本阶段实现“在文档列表点更新，界面自动带上 key”的完整交互。

### 不同情况会发生什么

- **不传 key，文件字节完全相同**：按源文件哈希识别相同文档，重新导入不会因为临时路径或文件名变化而得到另一份文档身份。
- **不传 key，内容变化**：作为新的文档身份；即便文件名相同，旧版也不会自动退役，检索可能同时看到新旧内容。
- **传相同 key，正文有小幅修订**：通常作为同一文档的新版本；不是保证每个块、每个切片编号都不变。
- **传相同 key，正文变得明显不同**：在索引替换前暂停，IR 标记为 `review_required`，保留旧索引和旧注册记录。
- **第一版未传 key，后来补传一个 key**：不会自动绑定原来的无键文档，需要受控迁移；当前没有一键补绑定能力。

正文差异保护是防误操作的启发式检查，不是“判断两份文档是否相同”的绝对证明：相似模板可能误通过，合法的彻底重写可能被拦截。没有上一版 IR 时，也无法执行这项检查。它不能代替用户身份与文档操作权限校验。

### 替换的范围与风险

替换的是目标索引中这份文档的旧检索切片，不是覆盖旧原文件。旧上传文件和旧 IR 制品仍保留，但这不等于已经具备完整版本管理和一键回滚。

当前版本替换尚不具备事务式切换和失败自动恢复的保证。更新失败仍可能造成检索内容缺失，因此生产切换必须保留可恢复的旧索引，不能只依赖旧文件还在。

多实例并发更新和权限隔离仍需生产加固；key 应由可信调用方在合适的命名空间内分配。当前实现不应直接视为可对外开放的生产文档管理服务。

## 五、实现范围

本阶段的实现主要集中在以下职责；公开版不列出内部源码位置，也不随本次提交发布功能代码：

- 文档模型与适配：统一 IR、MinerU/Markdown 适配、规范化和结构化切分。
- 身份与修订：文档身份、页面和内容块对齐、差异比较与异常修订保护。
- 导入与存储：上传参数、上一版 IR 注册、任务状态与索引适配。
- 查询兼容：读取新旧索引可用字段，返回来源信息。
- 测试与迁移：复杂文档样例、预期快照、IR 迁移与独立测试索引。

本阶段没有重写检索排序策略或 Agent 架构，也没有提前实现语义层、记忆、多 Agent 和完整知识生命周期。

以下是已有运行记录，不是编写这份说明时重新执行的测试：

- 已用实际文档制品验证章节、内容块、切片、表格与图片的结构化产出。
- 在已验证样例中，切片具备来源、页码和内容块定位信息。
- 在独立测试索引中验证了重复导入：记录数量与稳定切片身份保持一致，没有重复累积。

## 七、质量、延迟和成本：不能只看功能增加

### 历史阶段 0 基线

历史基线存在数据集一致性问题，因此不能把它当作严格同口径的前后实验。本阶段没有改写旧基线来消除这一问题。历史快照回放只能复核已保存输出，不能证明新代码的实时行为或新索引质量。

### 同日旧索引与新索引对照

已有服务运行使用同一当前数据集和同一提示词，对旧索引与新 IR 索引进行对照。这不是两套完整历史代码的严格 A/B 实验。公开版不披露具体业务样本、指标数值或内部报告，只保留影响结论的事实：

- 新索引的样例通过数低于旧索引，质量验收未通过。
- 回答正确性指标持平，但引用质量仍存在问题。
- 本次新索引的中位响应延迟更高，不能声称整体性能提升。
- 模型调用次数相同，token 消耗较少，但这不足以证明实际费用下降。

计价信息不足，不能把报告中的费用显示当作真实账单。两次均为单次小样本运行，LLM/Web 的非确定性和环境负载可能影响结果。

### 为什么不能把新索引的低分全部归因于格式

旧评测期望值含 Markdown 的 `#` 标题前缀和旧切片编号后缀，新 IR 使用结构化标题，造成部分检索及引用匹配误差。

对两份已有报告使用相同标题规范化规则做只读诊断后，部分指标改善，但新索引的样例通过数仍低于旧索引。

这个诊断没有修改答案、检索顺序、原始报告或冻结基线，也不是正式验收口径。仍存在真实的引用选择差异和其他失败样例，不能用标题格式解释掉全部问题；存在口径问题的指标不用于支持发布结论。

本地 IR 构建还增加了来源和身份处理开销；它与旧版仅对内存 Markdown 做切分并非同口径计时，不能直接声称解析速度提升或承诺生产延迟。

## 八、迁移、回滚与当前完成状态

当前保留旧集合为默认，没有把新影子集合切成正式索引，也没有覆盖阶段 0 基线。

正式迁移应保留旧索引，在独立新索引中重建同一批文档，核对数量、身份、引用和问答质量，再切换查询配置。确需回滚时切回保留的旧索引，并恢复相应代码和配置；不能把普通版本更新当作自带回滚能力。

在进入下一阶段或正式切换前，仍需处理：

- 新索引的引用选择和问答质量退化，完成可信的重复对照评测。
- 历史评测数据集一致性与来源匹配口径问题，保留原始记录而不是覆盖旧基线。
- 如需生产发布，补齐安全的索引切换、失败恢复和多实例并发保障。
- 如需面向用户直接更新文档，补齐文档列表与更新入口，以及相应权限控制。

因此，当前状态应表述为：**文档 IR 核心实现及结构验证已落地，真实入库和重复导入已验证；阶段 1 的整体质量发布门槛尚未通过。**
